## Why D0.5 exists

Dispatch 0 documented a cloud-staging environment as Halt 3 — a Ken-blocking step requiring AWS credentials and Terraform-provisioned RDS/S3/Redis. That made D01-D13 harder than necessary because most testing scenarios don't need cloud parity, just a real Postgres + Redis + S3 + SMTP + observability stack.

D0.5 inserts a sub-dispatch between D0 and D01 that delivers a complete local Docker Compose stack matching production behavior for ~80% of scenarios. Cloud staging becomes a Dispatch 14 production-parity prerequisite (DNS, TLS, managed-Postgres PITR, real PayMongo webhooks, SES email-domain reputation), not a D0 blocker.

## What D0.5 produces

Full stack:

## Open questions / known limitations

- **MinIO versioning vs Object Lock:** The local stack uses MinIO's versioning. Cloud staging in D14 must enable S3 Object Lock with 10-year retention for BIR receipts (per Bug 1325 + Dispatch 14). Local does not enforce retention.
- **Postgres PITR:** Not implemented locally (no backup tooling in dev). D14 production-parity adds PITR via managed Postgres or `wal-g`.
- **Real DNS / TLS:** Local uses HTTP and `localhost` hostnames. D14 adds `staging.api.onservice.ph` with ACM certificates.
- **PayMongo / Twilio webhooks:** Local stack cannot receive real webhooks from those services. D14 staging exposes a public TLS URL.
- **SMTP delivery:** MailHog captures locally; D14 wires real Postmark/SES with sender domain reputation.

These are explicitly NOT D0.5 concerns. They are D14 cutover items (per the original DISPATCH-0 Step 0.5 retained for D14 reference).
