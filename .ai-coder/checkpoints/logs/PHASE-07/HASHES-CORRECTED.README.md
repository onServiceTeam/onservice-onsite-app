## Why this file exists

The original `HASHES.sha256` in this directory was generated by an earlier
version of `verify-master.sh` whose `find` command included files that were
either (a) rewritten on subsequent verify-master invocations, or (b) added
or modified after the hash chain itself was generated. As a result,
`sha256sum -c HASHES.sha256` fails on a substantial portion of entries.

The discrepancy is not limited to the originally-suspected transient files
(`sanity-checks.log`, `verify-master-attempt-*.log`). It also affects
durable evidence artifacts such as `EVIDENCE-MANIFEST.md`,
`HONESTY-CHECK.md`, `gate-2-boundaries-*.md`, `gate-2-paper-trace-*.md`,
`gate-3-future-bugs.md`, `gate-3-premortem.md`, the `checks/INDEX.md`,
and various `preflight/*.log` files. The most plausible explanation is that
the AI coder ran `verify-master.sh` (which writes `HASHES.sha256`) BEFORE
the final pass of writing/editing the per-phase evidence documents, and the
hash file was never regenerated before the phase commit.

## What was preserved

The original `HASHES.sha256` IS PRESERVED unchanged as historical truth —
it records exactly what `verify-master.sh` emitted at the time of the
original phase commit, including the now-broken entries.

## Note on line endings

These hashes are computed against the working-tree representation on Windows
with `core.autocrlf=true` (CRLF line endings on disk). Verifiers on Linux/macOS
or with `core.autocrlf=input` may see hash mismatches because their working tree
will contain LF line endings instead. To verify on a non-Windows system, either:
  * temporarily set `git config core.autocrlf true` and re-checkout the file set,
    or
  * compute the canonical (LF) hash of each file via
    `git show HEAD:<path> | sha256sum` and compare.

The hash file itself is committed with LF line endings (as is normal for git).
